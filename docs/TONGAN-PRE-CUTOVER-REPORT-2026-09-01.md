**Seven real bugs were found and fixed during this walkthrough** (all staging-only; live system never touched):

1. **False CONFLICT badge on already-applied fields** (found during Test 5 re-check) — the conflict flag compared the live value against the original submission-time snapshot even after a field had already been applied, so a correctly-applied field could still show a red CONFLICT badge. Fix: once a field is `Applied To Live? = Yes`, compare live value against the *proposed* value instead. Committed `240e60a5`, redeployed, verified fixed live.
2. **Misleading "Partially approved" status on fully-conflict-blocked submissions** (found during Test 9) — a submission with 0 fields actually applied (all blocked by conflict) fell into a generic "Partially approved" label, implying something had been written when nothing had. Fix: added a distinct "Conflict — needs re-review" status, checked ahead of the Rejected/Returned branches, plus a matching filter option in the queue dropdown. Committed `62b4d23f`, redeployed, verified fixed live.
3. **Unguarded double-rollback** (found during Test 14) — `apiRollbackChange` always rewrites an audit row's original "Old Value" back to live with no check of what's currently live, and the UI kept offering the "Rollback" button on a row indefinitely, even after it had already been reversed once. A repeat click produced a harmless no-op in this case, but the same gap could silently discard a legitimate change made after the first rollback, with no warning. Fix (UI-only guard, backend write path unchanged): the Change Log now shows "Already rolled back" instead of an active button for any audit row that has already been reversed. Committed `e723135a`, redeployed, verified fixed live.
4. **Admin Users tab silently failed to load ("No response from server")** (found while adding the second test account for items 2/10-12) — `apiListAdminUsers` completed successfully server-side every time (confirmed via the Apps Script Executions log — every call showed `Completed`, no errors), but the browser never received usable data back. Root cause: the "Date Added" column is written as a plain `yyyy-MM-dd` string, but Sheets auto-detects that pattern and silently stores the cell as a real Date; a raw `Date` object nested in the returned row data corrupted the `google.script.run` response on the way back to the browser even though the server-side call logged as successful. Fix: `apiListAdminUsers` now converts any Date value to a plain string before returning. Also hardened the client: the Admin Users table now retries once on a malformed response and shows a clear "click Refresh to try again" message instead of crashing, and a manual Refresh button was added. Committed `0240d1cc` (client hardening) and `0ac5105f` (server fix), redeployed, verified fixed live — both accounts now display correctly.
5. **Cross-domain identity verification ("Verify with Google") never completed the round trip** (found while testing item 2 with the second account, `ronvave2011@gmail.com`) — a chain of four distinct issues, each uncovered only after fixing the previous one, since "Execute as: Me" can only resolve `Session.getActiveUser()` for same-domain (`@hawaii.edu`) accounts and a second, separately-deployed "Execute as: User accessing the web app" broker deployment was required to see any Google account:
   - Exact-string comparison of `ScriptApp.getService().getUrl()` never matched due to Workspace-domain URL canonicalization, so the app could not tell which deployment it was running as. Replaced URL-based branching with an explicit `?identitybroker=1` query parameter that only our own generated broker link ever sets. Committed `93de8fb7`.
   - Visiting the bare broker URL directly (no query param) fell through to the main app-shell branch and threw an uncaught Sheet-permission exception under the broker's execution mode. Hardened with a try/catch fast path (safe failure either way, just a UX cleanup). Committed `f2141def`.
   - The broker's return redirect used a plain, unsandboxed navigation call while the outbound "Verify with Google" button correctly targeted `window.top` — an asymmetry that, combined with the next issue, first looked like the culprit. Committed `058dff9d` (superseded by the real fix below once confirmed live via DevTools that this wasn't actually the blocker).
   - **Root cause, confirmed live via the browser DevTools console:** Apps Script serves every `doGet()` page inside a sandboxed, cross-origin (`script.googleusercontent.com`) iframe with the `allow-top-navigation-by-user-activation` sandbox flag. That flag silently blocks any script-triggered navigation of the whole tab that isn't inside a real click — so the broker's *automatic* redirect back threw an uncaught `SecurityError` and the page simply sat on "Verifying…" forever with no visible error. First fix: require a real "Continue" button click for the return trip, matching the outbound button (committed `3d27f6d9`). That fixed the *navigation*, but a second, deeper problem then surfaced: the token was being carried in a URL fragment (`#identity=...`), and a cross-origin sandboxed iframe can never read the top-level address bar at all — confirmed live, the fragment landed correctly in the address bar but the app's own script never saw it. **Final fix:** replaced the URL fragment entirely with an OAuth-style one-time code — the broker signs the identity, stores it server-side in `CacheService` keyed by a random UUID (2-minute TTL, single-use), and redirects back with only that code in a query parameter (`?identitycode=...`, which unlike a fragment IS sent to the server). `doGet()` on the main deployment redeems the code server-side and embeds the result directly into the rendered page before any client script runs — no cross-frame read of any kind remains in the flow. Committed `85b9d2f5`. Verified live end-to-end with the second account: signed in as `ronvave2011@gmail.com`, correctly resolved and displayed as Researcher, scholar picker loaded normally.
6. **No way to reactivate a deactivated Admin User** (found immediately after Test 2's deactivation check passed, while trying to re-role `ronvave2011@gmail.com` back to `Authenticator` for tests 10–12) — the app had `apiDeactivateAdminUser` and a "Deactivate" button for active rows, but no matching backend function, dispatcher entry, or UI control existed to reverse it; an inactive row only showed the bare role dropdown with no button. Fix: added `apiActivateAdminUser` (Owner-only, mirrors the deactivate function — sets `Active? = Yes`, clears `Date Deactivated`/`Deactivated By`), registered it in the `apiCall` dispatcher allowlist, added `bridge.activateAdminUser`, and an "Activate" button that renders in place of "Deactivate" for any inactive row. Committed `d12863d8`, redeployed, verified fixed live — "Activate" button appeared on the inactive row, click flipped it to `Active? = Yes`, and the role dropdown was then used to set it to `Authenticator` for tests 10–12.
7. **Owner could not see/use the conflict-resolution control after a normal page refresh** (found during Test 12) — the "Owner resolution note" input and "Owner: resolve conflict" button were only ever shown inside the browser tab that happened to submit the losing decision and receive the `status:'conflict'` response client-side; opening or reloading the case in any other tab or session — including the Owner's own, on the normal path any real Owner would use — never re-derived that state from the server, so the resolution row stayed hidden even though the resolve button's own visibility was correctly role-gated. A second, related issue: the Authenticator whose submission caused the conflict briefly saw the "Owner resolution note" input box exposed in their own window (the button itself stayed correctly hidden, so this was a display-only leak, not a functional one — `apiResolveIdentityConflict` was already Owner-gated server-side throughout). Fix: `openIdentityCase()` now inspects the case's actual decisions on every load and shows the resolution row only when a decision has `Conflict Escalated To Owner? = Yes` with no `Final Decision Date (UTC)` yet, and only for the Owner role — correct on fresh load, refresh, or in any tab, never derived from a local event. Committed `edc78ba1`, redeployed, verified fixed live and used to complete Test 12 successfully.
